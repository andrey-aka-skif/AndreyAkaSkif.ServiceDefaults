# Service Defaults OpenAPI

Единообразная конфигурация спецификации OpenAPI для ASP.NET Web-API приложений.
Спецификацию генерируют встроенные средства ASP.NET (`Microsoft.AspNetCore.OpenApi`).

Пакет самостоятельный: зависимости от `AndreyAkaSkif.ServiceDefaults` у него нет,
он может использоваться отдельно.

## Установка

```sh
dotnet add package AndreyAkaSkif.ServiceDefaults.OpenApi
```

Поддерживаются `net9.0` и `net10.0`. На `net9.0` подтягивается
`Microsoft.AspNetCore.OpenApi` 9.x, на `net10.0` — 10.x; публичный API пакета
на обеих ветках одинаков.

## Возможности
- спецификация с параметрами по умолчанию: `AddDefaultOpenApi()` / `UseDefaultOpenApi()`;
- спецификация с атрибуцией из конфигурации: `AddConfiguredOpenApi()` / `UseConfiguredOpenApi()`;
- описание конечной точки проверки жизнеспособности в документе:
  `AddHealthCheckEndpointDescription()`.

## Пример
```csharp
var builder = WebApplication.CreateBuilder(args);

// атрибуция документа берётся из секции "OpenApi"
builder.AddConfiguredOpenApi();

// описание конечной точки /health в документе, необязательно
builder.AddHealthCheckEndpointDescription();

var app = builder.Build();
app.UseConfiguredOpenApi();

app.Run();
```

Без конфигурации:

```csharp
builder.AddDefaultOpenApi();

var app = builder.Build();
app.UseDefaultOpenApi();
```

## Конфигурация

Секция `OpenApi`. Для `AddConfiguredOpenApi()` обязателен только `Title`:

```json
"OpenApi": {
    "Title": "Demo API",
    "Description": "Демонстрационный сервис",
    "DocumentName": "v1",
    "Version": "1.0",
    "Servers": [
        "/",
        "/api"
    ],
    "Visibility": "ByEnvironment"
}
```

| Ключ | По умолчанию | Что это |
| --- | --- | --- |
| `Title` | нет, обязателен | Заголовок документа. Без него приложение не стартует |
| `Description` | нет | Описание документа. Необязательно |
| `DocumentName` | `v1` | Имя документа и сегмент его адреса |
| `Version` | `1.0` | Версия контракта API |
| `Servers` | `/` | Адреса, по которым доступен сервис |
| `Visibility` | `ByEnvironment` | Доступность спецификации |

Отсутствующие обязательные параметры и невалидные данные роняют приложение на старте
хоста: выбрасывается `OptionsValidationException` со списком всех нарушенных правил.
**Следует обратить внимание,** что при использовании файлов конфигурации секция должна
быть указана в основном файле `appsettings.json`.
**Не следует** выносить секцию в файлы, содержащие среду. Например,
в `appsettings.Development.json`.

Пара `AddDefaultOpenApi()` / `UseDefaultOpenApi()` секцию не требует вовсе и читает
из неё единственный ключ — `Visibility`.

### Три версии, которые легко перепутать

Имя документа, версия контракта и версия сборки — разные вещи с разным темпом изменения,
и связывать их не следует.

**Имя документа** (`DocumentName`) попадает в адрес спецификации:
`/openapi/{DocumentName}.json`. Поэтому оно не должно зависеть ни от чего, что меняется:
по этому адресу генерируются клиенты, и его смена ломает их сборку. Значение `v1` —
принятый умолчательный идентификатор, а не «версия 1». Осмысленные альтернативы —
`internal` и `external`.

**Версия контракта** (`Version`) — поле `info.version` документа. По спецификации OpenAPI
это произвольная строка, а не номер: на числовые части она не разбирается, `2026-08` и
`1.0.0-preview.1` допустимы. Меняется, когда меняется контракт, а не когда выходит релиз.

**Версия сборки** задаётся при сборке и в спецификацию не попадает вовсе.

### Доступность спецификации

Ключ `OpenApi:Visibility` имеет три состояния, и отсутствие ключа — не то же самое,
что `Never`:

| Значение | Поведение |
| --- | --- |
| `ByEnvironment` (умолчание) | Вне `Production` спецификация доступна, в `Production` — нет |
| `Always` | Доступна в любой среде |
| `Never` | Не доступна ни в какой |

Поэтому в `appsettings.json` ключ обычно не записывают: значение по умолчанию задаёт среда,
а явное значение нужно лишь там, где среду надо перебить. Неизвестное значение роняет
привязку конфигурации — до валидатора оно не доходит.

В среде, где спецификация недоступна, конечная точка не формируется и запрос к ней
возвращает `404 Not Found`.

### UI не входит в пакет

Пакет формирует только JSON спецификации, она доступна по адресу `/openapi/{DocumentName}.json`.
Если нужен Swagger UI, используйте пакет `AndreyAkaSkif.ServiceDefaults.Swagger` — он
показывает документ по указанному адресу и с этим пакетом сочетается, а не заменяет его.
Показ UI управляется своим ключом, независимо от `OpenApi:Visibility`.

### Адреса серверов
Адреса в `Servers` следует задавать относительными: `"/"`, `"/api"`.

Swagger UI и другие клиенты берут базовый адрес запросов из первого элемента списка,
поэтому абсолютный адрес ломает работу везде, кроме прописанного адреса: за reverse proxy,
на другом хосте, а также при открытии страницы по https рядом с http-адресом
в конфигурации — браузер режет такой запрос как mixed content.

Относительный адрес допускается OpenAPI 3, и клиент резолвит его от адреса страницы:
запрос остаётся same-origin, то есть CORS не участвует.

Список необязателен. Если он пуст или отсутствует, подставляется адрес `"/"`.

### Описание конечной точки проверки жизнеспособности
`AddHealthCheckEndpointDescription()` добавляет в документ конечную точку `/health`
с единственным ответом `200 Healthy`. Метод только описывает конечную точку: чтобы она
работала, нужны HealthCheck сервисы и HealthCheck middleware в конвейере обработки
запросов. В ином случае конечная точка вернёт `404 Not Found`, а в Swagger UI
соответствующий пункт будет отвечать ошибкой.

Описание добавляется вручную потому, что конечную точку регистрирует промежуточное ПО,
а не обработчик minimal API: ApiExplorer её не видит, и генератор о ней не знает.

Адрес передаётся параметром и по умолчанию равен `/health` — тому же адресу, который
регистрирует `MapHealthCheckEndpoint()` из пакета `AndreyAkaSkif.ServiceDefaults`.
Значения должны совпадать; если приложение поднимает конечную точку по другому адресу,
его следует передать явно:

```csharp
builder.AddHealthCheckEndpoint();               // AndreyAkaSkif.ServiceDefaults
builder.AddHealthCheckEndpointDescription();    // этот пакет

var app = builder.Build();

app.MapHealthCheckEndpoint();                   // AndreyAkaSkif.ServiceDefaults
```

### Спецификация как файл-артефакт репозитория

Спецификацию можно собирать в файл при каждой сборке проекта и держать в репозитории:
тогда изменение контракта видно в диффе, а по файлу генерируются клиенты без запуска
сервиса. Методы этого пакета в такой сборке не участвуют — всё делает пакет
`Microsoft.Extensions.ApiDescription.Server`:

```sh
dotnet add package Microsoft.Extensions.ApiDescription.Server
```

```xml
<PropertyGroup>
  <OpenApiDocumentsDirectory>$(MSBuildProjectDirectory)/openapi</OpenApiDocumentsDirectory>
  <OpenApiGenerateDocumentsOptions>--file-name openapi</OpenApiGenerateDocumentsOptions>
</PropertyGroup>
```

Что стоит знать:

- каталог задаётся относительно файла проекта; без `--file-name` файл называется именем
  проекта, а при нескольких документах — `{Проект}_{ИмяДокумента}.json`;
- документ собирается запуском приложения в отдельном режиме, поэтому конфигурация должна
  быть валидной и на машине сборки: без `OpenApi:Title` упадёт не сервис, а сборка;
- ключ `Visibility` на генерацию файла не влияет — он управляет только конечной точкой;
- если документов несколько, а нужен один, его выбирает `--document-name`;
- версию спецификации в файле задаёт `--openapi-version` (например `OpenApi3_0`).

### Версия спецификации по таргетам
На `net9.0` генератор выдаёт документ OpenAPI 3.0, на `net10.0` — 3.1: это поведение
фреймворка, а не пакета. Если потребителю спецификации важна конкретная версия, её задают
явно — `--openapi-version` при сборке файла.
